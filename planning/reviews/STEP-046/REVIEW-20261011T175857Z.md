### F-001 — Файловый sink теряет existing mapping ошибок доступа и диска

**Severity:** medium
**Category:** implementation
**Location:** packages/logging/src/file-sink.ts:14
**Scenario:** Given Host задаёт logging.filePath на существующий файл, недоступный для записи; native append возвращает EACCES. / When createApplication создаёт файловый sink; тот же catch используется при отказе последующего append. / Then Наружу передаётся DOWNLOAD_ERROR, хотя существующий normalizeDomainError классифицирует EACCES как PERMISSION_DENIED.
**Expected:** Ошибки sink нормализуются через existing DomainError mapping: EACCES/EPERM → PERMISSION_DENIED, ENOSPC → DISK_FULL; raw exception и path не сериализуются.
**Observed:** Оба catch безусловно создают DownloadError(false, error). Реальный createApplication с временным readonly-файлом вернул DOWNLOAD_ERROR; cause.code был EACCES, normalizeDomainError(cause).code был PERMISSION_DENIED.
**Impact:** Host получает неверную стабильную классификацию причины отказа логирования и не может отличить отсутствие прав от общей ошибки загрузки; нарушен approved Implementation plan.
**Evidence kind:** reproduced
**Evidence source:** Approved STEP-046 Implementation plan, пункт 1, и собственный вызов real createApplication с readonly-файлом.
**Verification method:** Реальный filesystem EACCES во временном каталоге через экспортированный createApplication; сравнение с normalizeDomainError(error.cause).
**Verification result:** Подтверждено: DOWNLOAD_ERROR вместо PERMISSION_DENIED. Raw message/path в stdout проверки не выводились.
**Fix direction:** Использовать normalizeDomainError для native ошибки в обоих catch, сохранив безопасный DTO и fallback DOWNLOAD_ERROR для неизвестных причин. Проверить отдельные стабильные codes при создании и при append.
**Fingerprint:** sha256:6893e7007ecef5a46c7a05e5ed6c2c09f4d5bbb87bb6998389b3efd5ebe1a79e

**Confirmed preconditions:**
- logging.filePath создаёт createFileSink через composition-root.ts:44-46.
- В текущем runtime chmod(0400) действительно привёл appendFileSync к EACCES, что проверено по cause.code.

**Admissible alternatives:**
- Явно сохранить ту же existing mapping для подтверждённых filesystem codes в обоих catch без передачи raw native сообщения.

**Constraints:**
- Изменение ограничено packages/logging и связанными тестами STEP-046.
- PRN-002: native message, filePath и cause остаются вне публичной сериализации.
- Не вводить новую error hierarchy, location/rotation/retention policy.

**Evidence:**
- planning/tasks/STEP-046.md:112 требует нормализацию через existing DomainError mapping.
- packages/shared/src/errors.ts:139-145 сохраняет DomainError и отображает ENOSPC/EACCES/EPERM в DISK_FULL/PERMISSION_DENIED.
- packages/logging/src/file-sink.ts:13-14 и 22-24 обходят mapping через безусловный new DownloadError.
- Собственный runtime check: yarn node --input-type=module, exit 0; mkdtemp → writeFile → chmod(0400) → createApplication({stateDir, providerOverride:{}, logging:{filePath}}). Наблюдались applicationCode=DOWNLOAD_ERROR, nativeCode=EACCES, expectedFromExistingMapping=PERMISSION_DENIED; временные файлы удалены.
- packages/logging/src/file-sink.test.ts:39-43 проверяет только instanceof DomainError и не проверяет mapping.

### F-002 — Debug serializer копирует frames исходного Error вместо нормализованной DomainError

**Severity:** medium
**Category:** implementation
**Location:** packages/logging/src/serializers.ts:32
**Scenario:** Given Экспортированный serializeError получает обычный Error, созданный в libraryOnlyFrame(), и options.debug=true; такая форма вызова уже есть в serializers.test.ts. / When serializeError нормализует error для toJSON, затем вызывает safeStack с исходным error. / Then details.debug.stack содержит libraryOnlyFrame из исходного stack и не содержит frames созданной нормализованной DomainError.
**Expected:** Header и call frames берутся из нормализованной DomainError; исходный library error.stack и cause не копируются, как закреплено в пункте 2 плана.
**Observed:** normalizeDomainError(error).toJSON() теряет объект нормализованной ошибки, а safeStack(error, normalized) извлекает error.stack исходного аргумента. Runtime check дал rawDebugCopiesLibraryFrame=true и rawDebugContainsNormalizerFrame=false; при передаче заранее нормализованной ошибки получены обратные результаты.
**Impact:** Централизованный debug serializer не выполняет гарантированную планом границу источника stack: исходные библиотечные frames переходят в публичный DTO. Безопасность этой части зависит от предварительной нормализации вызывающей стороной.
**Evidence kind:** reproduced
**Evidence source:** Approved STEP-046 Implementation plan, пункт 2, и собственное сравнение экспортированного serializer на raw и normalized Error.
**Verification method:** Сравнение details.debug.stack raw Error и normalizeDomainError(raw) через экспортированный serializeError.
**Verification result:** Подтверждено копирование raw frame; application command path предварительно нормализует ошибку и в отдельном check секрет не раскрывает.
**Fix direction:** Сохранить нормализованный объект DomainError до toJSON и строить debug frames только из него; финальный DTO по-прежнему пропускать через redactor. Уточнить существующий serializer test проверкой отсутствия frame, присутствующего только в raw Error.
**Fingerprint:** sha256:35c392808628859d1f5aae82976db6e02a614cad17cf982a1ae27a0b954dce67

**Confirmed preconditions:**
- serializeError экспортирован из packages/logging и принимает unknown Error и optional debug без требования предварительной нормализации.
- В текущем runtime исходный Error имеет собственный call frame libraryOnlyFrame, отсутствующий у новой DomainError, что проверено двумя вызовами.

**Admissible alternatives:**
- Для raw Error возвращать только безопасный header, если frames нормализованного объекта недоступны, сохранив debug DTO contract.

**Constraints:**
- Сохранять CommandResult/JobEvent schemaVersion 1 и default отсутствие stack.
- Не переносить cause и исходные library messages.
- Не заявляется воспроизведённая утечка через ApplicationFacade: command уже передаёт normalized Error.

**Evidence:**

- packages/logging/src/index.ts экспортирует serializeError через export * from './serializers.js'; serializers.test.ts:40-48 уже вызывает raw Error с debug=true, но проверяет только удаление header message.
- Собственный runtime check: yarn node --input-type=module, exit 0; function libraryOnlyFrame(){return new Error('library-only header')}; serializeError(raw, undefined, {debug:true}) сохранил libraryOnlyFrame и не содержал normalizeDomainError. serializeError(normalizeDomainError(raw), undefined, {debug:true}) не сохранил libraryOnlyFrame и содержал normalizeDomainError.

**Severity:** low
**Category:** implementation
**Location:** packages/application/src/results.ts:58
**Scenario:** Given Application вызывается с logging.debug=true; resume получает несуществующий jobId и возвращает CommandRefusalError('JOB_NOT_FOUND'). / When command объединяет reason с debug для публичного DTO и пишет warning. / Then Публичная error.details.reason сохраняется, но debug warning получает прежний errorDto без объединённой reason. При debug=false reason есть в записи.
**Expected:** Debug warning содержит тот же безопасный error DTO, который получает клиент, включая совместно существующие details.reason и details.debug; включение debug не теряет диагностическую причину.
**Observed:** Ветка debug логирует {error:errorDto} до объединения details. Реальный api.resume(missing) дал publicReason=JOB_NOT_FOUND в обоих режимах; loggedReason=JOB_NOT_FOUND при debug=false и null при debug=true.
**Impact:** Debug-лог теряет стабильную причину отказа и не различает JOB_NOT_FOUND от LEASE_HELD_BY_OTHER_OWNER при общем VALIDATION_ERROR. Это наблюдаемая регрессия диагностики и расхождение с планом логирования того же DTO.
**Evidence kind:** reproduced
**Evidence source:** Approved STEP-046 Implementation plan, пункт 2, и собственный вызов real api.resume в обоих debug режимах.
**Verification method:** Сравнение возвращённого CommandResult и JSON warning capture реального application при debug=false/true.
**Verification result:** Подтверждено: debug добавляет stack, но удаляет reason только из лога; DTO сохраняет reason.
**Fix direction:** Собрать окончательный безопасный error DTO с mergedDetails до logger.warn и использовать его и в debug-логе, и в CommandResult; сохранить прежнюю форму обычного warning.
**Fingerprint:** sha256:1a9d8a71aaa5764ee9c9454793aedaf8d7a5a28616e556a1561d42e76cee0d90

**Confirmed preconditions:**
- createApplication разрешает logging.debug вместе с injected logger и передаёт debug в command.
- Несуществующий jobId в текущем application создаёт CommandRefusalError с JOB_NOT_FOUND; это наблюдалось в фактическом DTO.

**Admissible alternatives:**
- Добавить объединённую reason в debug error.details без изменения default logging, обеспечив совпадение details лога и возвращаемого DTO.

**Constraints:**
- Сохранить existing reason enum и v1 envelope.
- Не переносить owner/runtime/cause данные в лог.
- Исправление ограничено command boundary STEP-046 и её тестами.

**Evidence:**
- planning/tasks/STEP-046.md:129 требует объединение debug/reason без потери ключей и логирование того же безопасного DTO в debug.
- packages/application/src/results.ts:49-58 создаёт mergedDetails, но ветка debug передаёт первоначальный errorDto; строки 67-71 возвращают клиенту уже объединённые details.
- Собственный runtime check: yarn node --input-type=module, exit 0; real createApplication с providerOverride, временным stateDir и injected createLogger({sink}). api.resume('step046-lead-missing') при debug=false: publicReason=JOB_NOT_FOUND, loggedReason=JOB_NOT_FOUND; при debug=true: publicReason=JOB_NOT_FOUND, loggedReason=null, publicDebug=true, loggedDebug=true.
