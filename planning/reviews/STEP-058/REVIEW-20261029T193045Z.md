### F-001 — Сохранение открытых настроек отменяет подтверждённую тему sidebar

**Severity:** medium
**Category:** implementation
**Location:** apps/desktop/src/renderer/Settings.tsx:92
**Scenario:** Given Приложение запущено со светлой темой; пользователь открывает Настройки, и Settings сохраняет локальный value.theme=light. / When Пользователь включает тёмную тему переключателем sidebar, дожидается успешного saveSettings, затем нажимает «Сохранить настройки» в уже открытом Settings. / Then Settings повторно отправляет theme=light из локального снимка; сохранённая тема и весь интерфейс возвращаются к светлой без нового выбора пользователя.
**Expected:** Sidebar и вкладка «Внешний вид» используют единое подтверждённое состояние темы; сохранение остальных настроек не перезаписывает более позднее подтверждённое изменение темы.

Изолированный компонентный эксперимент получил settings.theme='light' после успешного sidebar dark и следующего save.
**Impact:** Обычная последовательность настройки приложения теряет явно сохранённую тему и нарушает Acceptance о сохранении темы и пункт 5 Ready plan об общем подтверждённом state.

**Verification result:** Exit 1: expected 'light' to be 'dark' на финальном assertion строки 19; предыдущий assertion подтверждает успешное сохранение dark.
**Fix direction:** Синхронизировать подтверждённую тему между App и Settings, сохранив осознанные несохранённые правки остальных полей; передавать актуальную тему/снимок либо исключать stale theme из сохранения, когда она не менялась в Settings.
**Fingerprint:** sha256:f690049d50256a934f7599b5a70eebc04aec80bfe22beed88025d410453065c8

**Confirmed preconditions:**
- Settings смонтирован до переключения sidebar, что является обычным доступным UI path.

**Admissible alternatives:**

**Constraints:**

- Сохранить OUTCOME_UNKNOWN без автоматического повтора mutation.

**Category:** implementation

**Scenario:** Given На экране загрузок доступно активное задание, и пользователь вызывает «Отменить». / When api.cancel подтверждает JobSnapshot со status=cancelled; core не публикует job.completed для cancel, после команды useDownloads перечитывает cancelled snapshot. / Then Список обновляется до cancelled, но notice остаётся undefined: completionPending заполнен только при job.completed, и условие уведомления никогда не выполняется.
**Expected:** Подтверждённая отмена показывает отдельное in-app уведомление info по REQ-058/макету09, без ложного успеха, дублей или повторного cancel.

Main уже обрабатывает подтверждённый cancel отдельно для OS notification, но renderer эквивалентной ветки не имеет.
**Impact:** Один из явно требуемых результатов макета09 недоступен в обычном UI; screenshot и текущий тест не подтверждают пользовательский сценарий отмены.
**Evidence kind:** reproduced

**Verification result:** Exit 1: jobs[0].status='cancelled' подтверждён; assertion notice.message содержит 'Отменено' не выполнен, поскольку notice undefined.
**Fix direction:** Учитывать подтверждённый результат cancel либо последующий authoritative cancelled snapshot в renderer notification flow, с существующей дедупликацией. Заменить/дополнить тест сценарием command('cancel') без искусственного job.completed.
**Fingerprint:** sha256:1433f31d1e0c947d85726a22d9784d65581d4a6b2e033e6ad00116a2319d14da

**Confirmed preconditions:**
- Core cancel не создаёт job.completed; проверено по manager terminal emission и существующей отдельной ветке main cancel.
- Результат cancel и следующий getDownload имеют status=cancelled; эксперимент подтверждает обновление jobs.

**Admissible alternatives:**
- Отдельная дедуплицированная ветка уведомления отмены в command после подтверждённого result/snapshot.

**Constraints:**
- Не менять lifecycle core и не придумывать новое terminal-событие ради UI.
