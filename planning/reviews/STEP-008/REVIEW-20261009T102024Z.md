### F-001 — Некорректный API-ответ не получает обязательное сообщение ADR-009

**Severity:** medium
**Category:** implementation
**Location:** packages/providers/yandex-music/src/auth-transport.ts:61
**Scenario:** Given getAccount использует действительный envelope и account/status возвращает HTTP 200 без обязательного displayName/login / When raw schema отклоняет ответ до библиотечной модели / Then наружу выходит PROVIDER_RESPONSE_INVALID с общим сообщением shared вместо обязательной диагностики изменения API
**Expected:** Для PROVIDER_RESPONSE_INVALID от API использовать сообщение ADR-009: «API Яндекс Музыки изменился. Текущая версия приложения не поддерживает новый формат ответа.»
**Observed:** getAccount возвращает code=PROVIDER_RESPONSE_INVALID, retryable=false, message=«Источник музыки вернул некорректные данные.»; выполнен один HTTP-запрос.
**Impact:** Публичная диагностика не соблюдает явно принятый контракт совместимости: пользователь не получает указание, что текущая версия приложения не поддерживает формат API.
**Evidence kind:** contract
**Evidence source:** Accepted ADR-009:66 и Ready STEP-008 implementation plan:118
**Verification method:** Минимальный вызов production compiled YandexMusicProviderAuth.getAccount с mock HTTP и несекретным envelope; .harness/local/step008-lead-review-repro.mjs
**Verification result:** Получено иное публичное сообщение при требуемом code; один запрос, без retry.
**Fix direction:** Создавать ошибки несовместимого API-ответа через приватный provider helper с обязательным сообщением и использовать его в raw/post-mapping auth schema branches; проверить message в одном тесте публичного getAccount.
**Fingerprint:** sha256:da58b09f4dc50722b33a24b83abfbbbe590df7faa16b3a49aae7b2725007e34b

**Confirmed preconditions:**
- Публичный getAccount получает valid credentials через существующий CredentialStore.
- HTTP transport hook реально пропускает status=200 до endpoint-specific raw schema.

**Constraints:**
- Сохранить code=PROVIDER_RESPONSE_INVALID и retryable=false.
- Не переносить raw response/Zod issues/cause в публичную ошибку.
- Исправление принадлежит provider STEP-008; менять shared/logger или non-auth provider не требуется.

**Evidence:**
- docs/adr/ADR-009-yandex-adapter-strategy.md:66 задаёт обязательное сообщение; planning/tasks/STEP-008.md:118 переносит его в implementation plan.
- packages/providers/yandex-music/src/auth-transport.ts:49-61 и yandex-music-auth.ts:225-226 создают общий ProviderError без изменения message; фактический shared constructor задаёт другое сообщение.
- node .harness/local/step008-lead-review-repro.mjs: malformed-200-account → PROVIDER_RESPONSE_INVALID, «Источник музыки вернул некорректные данные.», retryable=false, calls=1.
- auth-transport.test.ts:34-66 проверяет code при schema failure, но не обязательное message.

### F-002 — Envelope v1 записывается и читается с полем version вместо принятого schemaVersion

**Severity:** medium
**Category:** implementation
**Location:** packages/providers/yandex-music/src/auth-schemas.ts:64
**Scenario:** Given CredentialStore возвращает запись v1 в формате Accepted ADR-010: schemaVersion=1, accessToken, issuedAt и accountId / When после запуска getAccount валидирует запись / Then strict schema объявляет согласованный envelope повреждённым; собственная сериализация записывает иной discriminator version
**Expected:** Начальный private durable envelope v1 использует поле schemaVersion: 1, согласованное ADR-010; обязательные поля и неизвестная версия проверяются до использования.
**Observed:** Contract envelope отвергнут с PROVIDER_RESPONSE_INVALID до HTTP (calls=0); serializeCredentials создаёт ключ version и не создаёт schemaVersion.
**Impact:** Вводимый persistent формат расходится с Accepted ADR: корректная по контракту запись не восстанавливает сессию, а auth создаёт другой формат. Это расхождение data contract, а не стилистическое имя локальной переменной.
**Evidence kind:** contract
**Evidence source:** Accepted ADR-010: раздел «Формат, ошибки, logout и doctor», private envelope v1
**Verification method:** Публичный compiled getAccount получает literal ADR v1 envelope; приватный actual serializer показывает записываемые ключи; .harness/local/step008-lead-review-repro.mjs
**Verification result:** ADR envelope отклонён без HTTP, actual serializer использует иной discriminator.
**Fix direction:** Привести приватные serializer/schema и auth/session fixtures к schemaVersion: 1; сохранить fail-closed обработку неизвестной версии и проверить чтение/запись согласованного envelope после restart.
**Fingerprint:** sha256:78094c69dd59a7f58daebb2e11c2e86ba21804723cee441f9363d33aef67d967

**Confirmed preconditions:**
- Existing shared CredentialStore.read возвращает непрозрачную строку; provider владеет её форматом.
- Все обязательные поля contract envelope имеют валидные типы/значения; discriminator является единственным отличием от implementation fixture.

**Constraints:**
- Не переписывать Accepted ADR задним числом.
- Текущий STEP вводит первый product token storage; автоматический импорт/миграция plaintext и общая migration subsystem не нужны.
- Не расширять shared CredentialStore: envelope остаётся приватным provider.

**Evidence:**
- docs/adr/ADR-010-cli-auth-and-secure-storage.md:66 фиксирует private JSON envelope с schemaVersion: 1.
- packages/providers/yandex-music/src/auth-schemas.ts:62-71 требует version и strict; строка 86 записывает version: 1.
- node .harness/local/step008-lead-review-repro.mjs: adr-v1-envelope → accepted=false, PROVIDER_RESPONSE_INVALID, calls=0; written-envelope → keys=[version,accessToken,issuedAt,accountId].
- yandex-music-auth.test.ts:405-450 использует version в fixture и поэтому не обнаруживает drift относительно ADR.

### F-003 — OAuth отказ при выдаче device code классифицируется как повторяемая сетевая ошибка

**Severity:** medium
**Category:** implementation
**Location:** packages/providers/yandex-music/src/auth-transport.ts:67
**Scenario:** Given Начальный OAuth /device/code возвращает HTTP 400 с валидным error=access_denied либо invalid_client / When authenticate вызывает requestDeviceCode через authored transport и закреплённую библиотеку 0.3.0 / Then wrapper пропускает любой HTTP 400, library выдаёт BadRequestError, а normalizeAuthError превращает явный auth refusal в NETWORK_ERROR retryable=true
**Expected:** Подтверждённый OAuth auth refusal даёт AuthenticationError/AUTH_ERROR без retry; transport network/service failures остаются отдельно классифицированными.
**Observed:** Оба явных OAuth refusal сценария дают NETWORK_ERROR retryable=true, calls=1, writes=0, browser opens=0.
**Impact:** Caller получает неверный безопасный код и признак повторяемости вместо неретрайного отказа авторизации. Это нарушает принятую классификацию и может направить восстановление по сетевому пути.
**Evidence kind:** reproduced
**Evidence source:** Минимальный публичный authenticate на actual compiled provider + pinned library с mock OAuth /device/code HTTP 400
**Verification method:** node .harness/local/step008-lead-review-repro.mjs; два валидных OAuth error responses, request/native-write/browser counters
**Verification result:** Оба explicit refusal ответа стали повторяемым NETWORK_ERROR; одна попытка HTTP, без native writes или browser launch.
**Fix direction:** Классифицировать валидные OAuth error responses в transport по endpoint и error до потери статуса библиотекой; для device-code auth refusal выдавать AuthenticationError с инструкцией повторной авторизации. Добавить один публичный authenticate test для начального HTTP 400 refusal.
**Fingerprint:** sha256:c9d83c63cf3e9163fa5d758cf32053c9beb9a98036d211cb4c8679fc557759f6

**Confirmed preconditions:**
- authenticate сначала вызывает requestDeviceCode, поэтому /device/code failure достигает normalizeAuthError без browser/polling.
- Error JSON валиден для oauthErrorSchema; local wrapper пропускает статус 400 к actual pinned library.

**Constraints:**
- Сохранить authorization_pending и slow_down как управляющие ответы token polling.
- HTTP 429/5xx и настоящая сеть не должны становиться AUTH_ERROR.
- Сохранить retries: 0 и не экспортировать library exceptions/raw OAuth messages.

**Evidence:**
- docs/adr/ADR-009-yandex-adapter-strategy.md:59 и ADR-010 auth/storage error policy требуют confirmed OAuth refusal → AUTH_ERROR без retry; STEP-008 Scope:69 требует нормализацию auth ошибок.
- packages/providers/yandex-music/src/auth-transport.ts:63-73 исключает все status=400 из собственной классификации; yandex-music-auth.ts:233-243 знает DeviceAuthError, но не исходный BadRequestError.
- Actual installed @dvxch/yandex-music@0.3.0 src/methods/deviceAuth.ts requestDeviceCode не оборачивает BadRequestError; это оборачивание есть только в pollDeviceToken.
- node .harness/local/step008-lead-review-repro.mjs: device-code-refusal access_denied/invalid_client → NETWORK_ERROR, retryable=true, calls=1, writes=0, opens=0.
- yandex-music-auth.test.ts:167-195 проверяет access_denied только на /token после успешного device code.

### F-004 — Отмена авторизации во время account-запроса сохраняет credentials

**Severity:** medium
**Category:** implementation
**Location:** packages/providers/yandex-music/src/yandex-music-auth.ts:88
**Scenario:** Given Один authenticate уже получил OAuth token; приватная страница ещё открыта, а account/status ожидает ответа. Пользователь владеет этой страницей и может нажать её кнопку отмены. / When Пользователь отправляет POST по существующему private /cancel и получает 204, затем account/status возвращает корректный ответ. / Then authenticate выполняет CredentialStore.write, активирует новую запись и завершается успехом.
**Expected:** Согласно ADR-010 отмена до завершения flow прекращает авторизацию с AUTH_ERROR, не сохраняет новые credentials и не объявляет auth успешным.
**Observed:** Controller отмены привязан только к OAuth Client. this.account(accessToken) создаёт отдельный Client без flowSignal; после account-запроса нет проверки отмены перед write. Воспроизведение: cancelHTTP=204, accountAborted=false, nativeWrites=1, authenticate=resolved.
**Impact:** Новая постоянная авторизация сохраняется после явной отмены пользователя; может заменить прежнюю запись, хотя завершение flow не было разрешено. Секреты не утекли в stdout: дефект находится на границе отмены flow и сохранения credentials.
**Evidence kind:** reproduced
**Evidence source:** ADR-010 и локальный reproducer production dist YandexMusicProviderAuth
**Verification method:** node --input-type=module < .harness/local/step008-security-cancel-repro.mjs; первоначально исполнено эквивалентным inline heredoc из корня репозитория, с mock fetch/store и реальным private HTTP server.
**Verification result:** {"cancelHTTP":204,"accountAborted":false,"nativeWrites":1,"authenticate":"resolved"}; exit code 0
**Fix direction:** Распространить состояние отмены на проверку account и проверить его до сохранения/публикации новых credentials. Добавить узкую проверку: задержанный account, успешный POST /cancel, затем ответ account — AUTH_ERROR, write=0, прежняя запись сохранена, server закрыт.
**Fingerprint:** sha256:96a12b93a8d13e6000b295dd281a768975fc553bd13811481c53a2ac23f377b2

**Confirmed preconditions:**
- Единственный authenticate получил валидные device/token ответы.
- Account HTTP response задержан, что оставляет private page открытой.
- Пользователь отправляет корректную отмену со своей private page до завершения authenticate.

**Constraints:**
- Не расширять shared authenticate API и не добавлять CLI/desktop scope.
- Сохранить прежнюю запись до успешного разрешённого auth и существующую безопасную нормализацию ошибок.

**Evidence:**
- docs/adr/ADR-010-cli-auth-and-secure-storage.md: Decision / Flow и приватный challenge: отмена не пишет credentials и не объявляет auth успешным.
- packages/providers/yandex-music/src/yandex-music-auth.ts:78,88-94; account() создаёт this.client(accessToken) без controller.signal.
- .harness/local/step008-security-cancel-repro.mjs
- .harness/local/step008-security-cancel-repro-output.txt; фактически захваченный stdout, exit code 0.

### F-005 — Canary-проверка содержит пустые подставные артефакты

**Severity:** medium
**Category:** evidence
**Location:** packages/providers/yandex-music/src/yandex-music-auth.test.ts:619
**Scenario:** Given успешный Device Authorization с известными access, refresh, device и user canary / When проверяется отсутствие секретов в наблюдаемых поверхностях / Then проверяются только реальные outputs provider и отсутствие его дисковой записи; future publishers не входят в STEP-008
**Expected:** В STEP-008 доказательство должно соответствовать ограниченной provider/persistence поверхности: реальные notify, Account, safe error и captured stdout/stderr; отсутствие файлового writer подтверждается I/O capture либо отсутствием filesystem imports. Settings, manifest и event publishers принадлежат будущим STEP-017/018/019.
**Observed:** Тест корректно перехватывает console/stdout/stderr и реальные notify/Account, но добавляет в проверяемый объект литералы `settings: {}`, `logs: []`, `manifest: {}`. Они не создаются и не читаются продуктовым кодом. Проверка source подтвердила отсутствие filesystem imports и writer API в `packages/providers/yandex-music/src` и `packages/persistence/src`; однако текущий тест этого факта не выражает.
**Impact:** Литералы создают ложное evidence для future артефактов. Это не требует реализации или integration-тестов settings/manifest/events, но нужно сузить текущую проверку до наблюдаемой поверхности STEP-008.
**Evidence kind:** contract
**Evidence source:** STEP-008 bounded Scope/Implementation plan and current test's observable assertion
**Verification method:** read-only inspection of the test and its inputs
**Verification result:** The asserted settings/logs/manifest values are local empty literals, while scoped source has no filesystem writer/path.
**Fix direction:** Удалить пустые `settings/logs/manifest` literals. Оставить assertion над настоящими `notices`, `output`, Account и safe error; минимально добавить capture отсутствия disk write либо узкую проверку отсутствия filesystem imports у auth/provider/persistence source.
**Fingerprint:** sha256:3cee97cfb3b50ab29544f30062fe3e059e1947c97e3e06ee5ad6d37dfb012b9b

**Admissible alternatives:**
- Узкий source-level guard на отсутствие `node:fs` и filesystem writer imports в STEP-008 source.
- Тестовый I/O seam, который падает при попытке disk write во время auth flow.

**Constraints:**
- Не расширять реализацию CLI, manifest, events или application за Scope STEP-008.
- Не требовать integration-тестов для future publishers STEP-017/018/019.

**Evidence:**
- packages/providers/yandex-music/src/yandex-music-auth.test.ts:619-628
- planning/tasks/STEP-008.md:65-97 and 160-174
- packages/shared/src/provider.ts:17-27
- read-only source search: no filesystem imports or writer API in scoped provider/persistence source
