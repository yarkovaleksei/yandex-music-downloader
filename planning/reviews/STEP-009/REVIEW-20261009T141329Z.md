### F-001 — Старый metadata-запрос восстанавливает предыдущий аккаунт после logout и новой авторизации

**Severity:** medium
**Category:** implementation
**Location:** packages/providers/yandex-music/src/yandex-music-auth.ts:250
**Scenario:** Given Metadata-запрос A ожидает ответ на одном публичном provider; credentials A действительны. / When Caller выполняет logout, authenticate B и metadata B, затем завершается старый запрос A. / Then Следующий metadata request отправляет credentials A, хотя store содержит B.
**Expected:** Завершение старой metadata операции не меняет текущую сессию B.
**Observed:** getTrack захватывает credentials A в metadataRequest:241 и ожидает SDK/transport. logout:141-145 очищает active/store, authenticate:113-118 записывает и активирует B. Когда прежний getTrack завершается, новая строка metadataRequest:250 без проверки текущего session owner присваивает active=A. Следующие getTrack/getAlbum/getPlaylist читают этот active в readCredentials:222-227 и отправляют Authorization A. Достаточна задержка корректного ответа, malformed payload или доступ к private fields не требуются.
**Impact:** После успешного перехода на B новые metadata операции снова выполняются от A, хотя secure-store envelope содержит B. Это откат in-memory auth state и нарушение current-account scoping: доступность/приватные metadata могут быть получены с прежними credentials. Audio behavior будущего STEP-010 для finding не используется.
**Evidence kind:** reproduced
**Evidence source:** Независимый security reviewer: public-facade Node reproducer текущего canonical build, без private mutation.
**Verification method:** Задержанный synthetic metadata A; public logout/authenticate B; metadata B; завершение A; следующий metadata.
**Verification result:** metadataRequestSessions=[A,B,A], store=B, externalNetworkCalls=0, exit=0.
**Fix direction:** Удалить запись active credentials при завершении metadataRequest: read-only metadata операция не владеет переходом auth state. Добавить один public-facade offline regression для указанной последовательности.
**Fingerprint:** sha256:afd5cc019eaf6860c464005b7f9bf84a53bd2e504f81a4865409ae671e8a2679

**Confirmed preconditions:**
- Один публичный экземпляр YandexMusicProvider обслуживает metadata-запрос с действующими credentials аккаунта A.
- Ответ этой операции задерживается; SDK retries выключены, сериализации публичных auth/metadata вызовов и session-generation guard нет.
- Пока ответ ожидается, caller выполняет logout, затем успешно authenticate аккаунта B на том же экземпляре.
- Credentials A остаются действующими на сервере после локального logout; действующий контракт logout очищает local store/memory, а remote revoke не выполняет.

**Constraints:**
- Исправление ограничить новой metadata интеграцией STEP-009; accepted auth policy и ранее завершённые auth/browser modules не менять.
- Использовать synthetic SDK/transport responses, без повторного live/native/platform login.

**Evidence:**
- Текущий source path: getTrack:152-165 -> metadataRequest:240-251 -> readCredentials:220-233 -> Client(token) -> API request.
- Собственный diff против RUN snapshot подтверждает, что metadataRequest и присваивание active на его completion добавлены именно STEP-009. Прежние auth/browser/resolver modules не переаудировались.
- Минимальный Node --input-type=module reproducer импортировал текущий dist/index.js после canonical build и вызывал только публичные getTrack/logout/authenticate, с настоящим SDK и synthetic CredentialStore/fetch/browser; private fields не менялись.
- Captured observation: metadataRequestSessions=[A,B,A] после последовательности pending metadata A -> logout A -> authenticate B -> metadata B -> completion old A -> next metadata; store оставался B. Exit code 0, externalNetworkCalls=0. Синтетическая сессия очищена; реальные credential/native/login данные не использовались.
