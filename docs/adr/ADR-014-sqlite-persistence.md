# ADR-014 — SQLite persistence, общий каталог состояния и миграции

## Context

[REQ-033](../requirements/REQ-033-persist-sqlite.md) требует, чтобы SQLite-реализация `ManifestStore` стала единым источником истины для job, manifest и аренды одновременно для CLI и desktop, с миграциями N → N+1, без пересоздания базы и без токенов. [OQ-006](../open-questions/OQ-006-sqlite-headless.md) отложил SQLite до desktop без изменения семантики manifest. [ADR-004](ADR-004-atomic-finalization-and-manifest.md) задаёт manifest v1, аренду (PID, время старта, hostname, heartbeat) и control-запросы; [ADR-006](ADR-006-download-lifecycle-and-recovery.md) — recovery.

Headless MVP принят ([STEP-027](../planning/tasks/STEP-027.md)) на файловом хранилище: `FileManifestStore`, control inbox, kernel lock через `fs-native-extensions` и каталог `resolveStateDirectory()` (`%LOCALAPPDATA%\music-downloader`, `~/Library/Application Support/music-downloader`, `$XDG_STATE_HOME/music-downloader`). Composition root `packages/application` по умолчанию сам создаёт stores из `packages/persistence`. ESLint boundaries запрещают `apps/*` импортировать persistence, а application — native bindings напрямую.

## Problem

Нужно выбрать:

- SQLite-библиотеку, работающую и в Node.js CLI, и в Electron;
- расположение базы, общее для CLI и desktop;
- модель конкурентного доступа нескольких процессов, в том числе разных версий клиента;
- систему миграций;
- перенос существующих файловых manifest.

При этом контракт `ManifestStore` и семантика ADR-004 не меняются.

## Decision

### Библиотека и сборка

Используется `better-sqlite3` major 13 — первая версия на Node-API (N-API), с prebuilt binaries в пакете. Точную версию закрепляет STEP-029.

Зависимость добавляется только в `packages/persistence` (ADR-001 п.4). Store создаёт application composition root по умолчанию, как сейчас `FileManifestStore`. `apps/*` store не создают и не импортируют. Node-API binding, одинаковый для Node.js и Electron, не считается runtime-специфичной реализацией в смысле ADR-001 п.2, поэтому через `runtimeAdapters` его не передают. Синхронный API приемлем, потому что store выполняется вне UI-потока: в процессе CLI и в application host desktop (ADR-015).

Автор библиотеки пишет, что совместимость N-API binary с Node.js и Electron ожидается «теоретически». Это основание выбора, а не доказательство. Поэтому:

- STEP-029 доказывает загрузку и тесты на Node.js `>=22.13.0 <25` для Windows x64, macOS arm64/x64 и Linux x64;
- STEP-030 доказывает загрузку того же пакета в Electron `utilityProcess` на тех же платформах.

Если binary не загружается в каком-то runtime, это blocker и повод для нового ADR. Тихого перехода на JSON, WASM или другую библиотеку нет.

### Расположение и общий каталог состояния

База одна на пользователя ОС: `<stateDir>/state.sqlite3`. `stateDir` вычисляет существующий `resolveStateDirectory()`, одинаково для CLI и desktop. Desktop не хранит доменное состояние в Electron `userData`: тот каталог остаётся только для данных Chromium/Electron.

Поддерживается только локальная файловая система. Сетевые и синхронизируемые каталоги для базы не поддерживаются; обнаруженная ошибка блокировки — безопасная ошибка store. Способ упаковки не должен виртуализировать или изолировать `stateDir` между CLI и desktop. Ограничение для STEP-034/035: без MSIX AppData-виртуализации, Mac App Sandbox, Flatpak/Snap confinement — либо новый ADR.

### Режим доступа и разные версии клиентов

При открытии базы задаются `journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON` и конечный `busy_timeout`. CLI и desktop могут одновременно работать с одной базой. Записи выполняются короткими транзакциями; захват и изменение аренды — в `BEGIN IMMEDIATE`. Сетевые вызовы и запись аудио внутри транзакции не выполняются.

Каждая транзакция записи (сохранение manifest, захват аренды, heartbeat, control-запрос, настройки) сначала сверяет `user_version` с версией схемы процесса. При расхождении она отказывает безопасной ошибкой несовместимости и ничего не пишет. Долгоживущий процесс старой версии, открывший базу до миграции, перестаёт писать после неё.

### Роль SQLite относительно manifest

SQLite заменяет файловые manifest. Отдельной копии manifest в файлах нет.

- **Manifest v1** хранится как валидированный JSON-документ ADR-004 на job (поле `version` сохраняется), рядом — индексируемые служебные колонки (jobId, статус, время). Каждый переход состояния — одна транзакция, которая заменяет атомарную запись «temp + rename». Manifest неизвестной более новой версии не перезаписывается (`ValidationError`), как в ADR-004.
- **Аренда** — строка job с PID, временем старта процесса, hostname, временем захвата и heartbeat. Атомарность захвата и конкурентного перехвата устаревшей аренды обеспечивает транзакция SQLite вместо kernel lock на mutex-файле. Правила устаревания и матрица команд ADR-004/ADR-006 не меняются; аренда с другого хоста снимается только явной командой.
- **Control-запросы** — строки с уникальным `requestId`. Читает, применяет и удаляет их только держатель аренды; подтверждение записывается в той же базе. `sendControl` и `waitControlAck` сохраняют контракт.
- **Прочие данные в той же базе:** история, очередь, настройки (desktop `settings` хранятся в SQLite, а не в `settings.json`) и безопасная диагностика provider.
- **Остаются в файловой системе:** аудиофайлы, `.part` и байты обложек. Файловый cache метаданных и обложек с TTL этим ADR не переносится.

Shared-контракт `ManifestStore` не меняется. Core от SQLite не зависит.

### Миграции

- Версия схемы БД — целое число в `PRAGMA user_version` плюс таблица применённых миграций (номер, время). Она независима от версии manifest v1 и `PROVIDER_SCHEMA_VERSION`.
- Миграции forward-only, упорядоченные в коде. Каждая N → N+1 выполняется в своей транзакции вместе с обновлением `user_version`. Пропуск промежуточных версий запрещён. Новая база создаётся последовательным применением миграций с версии 1.
- Перед первой миграцией существующей базы делается резервная копия средствами SQLite (online backup или `VACUUM INTO`) рядом с базой, с номером исходной версии. Если копия не создана, миграция не начинается.
- При ошибке шага база остаётся в последней успешно применённой версии, процесс отказывает безопасной ошибкой, следующий запуск продолжает с этой версии.
- Если версия базы новее поддерживаемой, store сначала проверяет её и отказывает с понятной ошибкой несовместимости, не выполняя записей и миграций. База не пересоздаётся и не удаляется; downgrade не поддерживается.
- Повреждённая база не пересоздаётся автоматически; восстановление — явное действие пользователя с сохранённой копией.

### Перенос файловых manifest headless MVP

Импорт идемпотентен (ключ — jobId + hash исходного файла) и повторяется при каждом открытии базы для ещё не импортированных manifest:

- импортируются валидные manifest v1 без активной файловой аренды;
- job с живой, неизвестной или чужой (другой хост) арендой пропускаются до следующего открытия и попадают в безопасную диагностику;
- исходные файлы не удаляются и не изменяются, факт импорта (путь, hash) записывается в базу; импортированный manifest больше не читается как источник истины;
- нераспознанные или повреждённые файлы не импортируются и попадают в безопасную диагностику.

`FileManifestStore` остаётся источником импорта и сохраняет свои contract-тесты, пока поддерживается импорт. Одновременная работа старой CLI-версии на файловом store и новой версии на SQLite не поддерживается.

### Секреты

В схеме нет колонок для токенов, cookies, Authorization, credentials, signed URL с security-параметрами и ключей расшифровки (PRN-002). Credentials остаются в системном хранилище (ADR-010, ADR-015). STEP-029 добавляет автоматическую проверку, что в файлах базы, WAL и резервных копиях нет секретов из тестовой фикстуры.

## Alternatives considered

### Встроенный `node:sqlite`

Плюс — нет внешней native-зависимости. Минусы: в поддерживаемом диапазоне Node.js 22 модуль ещё в активной разработке, а его доступность в Electron runtime для проекта не подтверждена. Может быть пересмотрен новым ADR при стабилизации и проверке в Electron.

### `sql.js` / WASM SQLite

Нет native-сборки, но база живёт в памяти процесса и выгружается целиком, без файловой блокировки SQLite между процессами. Это несовместимо с одновременной работой CLI и desktop и с моделью аренды. Отвергнуто.

### `sqlite3` (node-sqlite3)

Тоже Node-API и асинхронный API, но проект deprecated, а его репозиторий архивирован. Отвергнуто как неподдерживаемая зависимость.

### Сохранить файловые manifest и добавить SQLite только для истории и настроек

Даёт два источника истины для job и противоречит REQ-033. Отвергнуто.

## Consequences

- Native-зависимость становится условием работы persistence в CLI и desktop. Отсутствие prebuilt binary для платформы требует toolchain сборки при установке. Упаковка native-модулей — STEP-034/035.
- Один store и одна модель аренды для CLI и desktop. Kernel lock остаётся только у файлового источника импорта.
- После миграции старая версия клиента отказывает писать, пока её не обновят. Порядок обновления CLI и desktop нужно учесть в STEP-034/036.
- Тесты persistence должны покрывать:
  - конкурентный захват аренды двумя процессами на SQLite;
  - отказ записи соединения, открытого до миграции другим процессом;
  - POSIX-права `0700`/`0600` на `stateDir`, базу, WAL, SHM и резервные копии.

## Security implications

База находится в пользовательском каталоге состояния. Права не слабее текущего файлового store:

- POSIX: `stateDir` создаётся или проверяется с режимом `0700`; `state.sqlite3`, `-wal`, `-shm` и резервные копии получают `0600` (создание под umask `077` или `chmod` до записи данных);
- Windows: наследование ACL пользовательского профиля `%LOCALAPPDATA%`.

Шифрование базы не вводится, потому что секретов в ней нет. Пути и названия треков считаются пользовательскими данными, не секретами, и не логируются сверх существующей политики. Raw SQLite/native messages не сериализуются в диагностику, события и ошибки.

## Data / migration implications

Новая схема v1 и импорт файловых manifest v1 (см. Decision). Семантика manifest v1 сохраняется, поэтому recovery ADR-006 работает поверх импортированных данных. Отката на файловое хранилище нет; резервная копия перед миграцией — путь восстановления.

## Compatibility / operational implications

Основания: [better-sqlite3 v13.0.0 — переход на N-API и встроенные prebuilt binaries](https://github.com/WiseLibs/better-sqlite3/releases). Платформенная проверка — STEP-029 (Node.js) и STEP-030 (Electron). Существующие CLI-команды, `--json` и семантика `resume`/`retry`/`cancel` не меняются. ADR-004 не supersede-ится: меняется механизм хранения, а не его контракт.
