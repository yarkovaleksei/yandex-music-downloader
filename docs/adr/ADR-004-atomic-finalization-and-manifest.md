# ADR-004 — Атомарная финализация файлов, manifest и владение job

## Context

Brief §17–§18: файл не пишется сразу под конечным именем, прерывание не должно терять операцию, headless MVP допускает файловые JSON manifest, SQLite появляется на этапе desktop. CLI-команды `resume`, `retry`, `cancel` запускаются отдельными процессами, демона в MVP нет.

## Problem

Нужно зафиксировать протокол записи файла, семантику manifest и модель владения job так, чтобы два процесса не повреждали один job, а recovery был корректным.

## Decision

**Запись файла.** Поток пишется в `*.part` в том же каталоге, что и итоговый файл (чтобы rename был атомарным в пределах файловой системы). Имя `.part` уникально для job и трека (в имя включается короткий идентификатор job и позиция трека перед суффиксом `.part`), чтобы разные job с одним итоговым путём не писали в один файл. После получения потока: закрыть поток → flush → проверить файл → записать метаданные и обложку (метаданные пишутся с явным указанием контейнера, а не по расширению `.part`) → финальная проверка → атомарный rename `*.part` → итоговое имя. Rename — точка фиксации: после него трек считается `completed` независимо от cancel. При перезаписи существующего файла (`--overwrite`) прежний файл остаётся нетронутым до rename. Cancel удаляет `.part`; pause его сохраняет.

**Manifest v1.** Документ job: `version`, `jobId`, `provider`, `source`, неизменяемый `plan` (отделён от изменяемого state), настройки качества и назначения, `control` job (ADR-003) и для каждого трека (ключ — позиция в плане) — статус, `retryPhase`, выбранный `AudioVariant` с `variantKey`, итоговый путь, число попыток и их история, последняя нормализованная ошибка, отметки времени и необязательное поле `partial { bytes, expectedSize, variantKey, tagged }`. Manifest не содержит токенов, cookies, signed URL и других секретов. Manifest с неизвестной более новой версией не перезаписывается (`ValidationError`). Записи атомарны (временный файл + rename) при каждом переходе состояния; частые обновления прогресса (`partial.bytes`) объединяются по времени и не пишутся на каждый чанк.

**Владение job.** В MVP нет демона. Контракт `ManifestStore` включает эксклюзивную аренду job (lease): lock-запись с PID, hostname, временем захвата и heartbeat; устаревание аренды определяется ниже. Только владелец аренды пишет manifest и `.part`. Не-владельцы никогда не пишут manifest: они отправляют control-запросы через отдельный канал `ManifestStore` — атомарно создаваемые уникальные записи на job; их читает и удаляет только держатель аренды и отражает результат в manifest. Отправитель ждёт подтверждения с таймаутом. Матрица команд:

| Состояние job | `resume` | `pause` / `cancel` / `retry` |
|---|---|---|
| живой владелец, `control = running` | ошибка «уже выполняется» | control-запрос владельцу |
| живой владелец, `control = paused` | control-запрос владельцу | control-запрос владельцу |
| живого владельца нет | процесс захватывает аренду и исполняет job сам | процесс захватывает аренду и применяет команду |

Recovery выполняется при любом захвате аренды. Аренда считается устаревшей, если heartbeat просрочен (таймаут определяется в STEP-016) и процесс-владелец на том же хосте не существует либо его PID принадлежит другому процессу (хранятся PID и время старта процесса); аренда с другого хоста снимается только явной ручной командой. Одновременный захват устаревшей аренды двумя процессами разрешается атомарной операцией, побеждает один. SIGINT владельца = `pause` job (ADR-003).

**Recovery и Range.** При захвате аренды сверяется окно «rename выполнен, manifest не записан» только для трека в `processing`: `.part` отсутствует, итоговый файл существует, проходит проверку и совпадает с ожидаемым размером/маркером идентичности, записанным в manifest до rename → `completed`. Для других состояний наличие итогового файла не превращается в `completed` (возможна перезапись `--overwrite` или чужой файл). Range-resume допустим только для `.part`, у которого `tagged = false`, совпадают `variantKey` и `expectedSize` и provider подтвердил `acceptsRanges`; иначе загрузка начинается заново.

**Хранилище.** Core работает через порт `ManifestStore`; в headless MVP реализация файловая (OQ-006 разрешён), в desktop добавляется SQLite-реализация без изменения семантики manifest и аренды. Каталог состояния настраивается; значение по умолчанию выбирается по правилам ОС (определяется в STEP-016).

## Alternatives considered

### Запись сразу под конечным именем

Прерывание порождает «успешные», но битые файлы; отвергнуто.

### SQLite с первого дня

Усложняет проверку концепции headless core; допустимо позже за тем же портом.

### Фоновый демон, владеющий всеми job

Упрощает управление, но усложняет установку и выходит за рамки headless MVP; отвергнуто для MVP.

## Consequences

Положительные: отсутствие повреждённых финальных файлов, безопасное восстановление, защита от двух писателей, заменяемое хранилище. Отрицательные: необходимость кросс-ОС проверки атомарного replace (особенно Windows), реализации аренды и очистки `.part`.

## Security implications

Manifest, lock-записи и `.part` не содержат секретов; права на каталог состояния соответствуют правам пользователя.

## Data / migration implications

Версионирование manifest обязательно; миграция manifest выполняется явной логикой, а не пересозданием.

## Compatibility / operational implications

Формат manifest v1 и протокол аренды — часть контракта resume между версиями приложения; несовместимая версия диагностируется явной ошибкой.
