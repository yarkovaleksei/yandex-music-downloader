# Автоматическая приёмка STEP-027 на Windows и macOS

Коллеге передаётся новый архив `STEP-052-acceptance.zip` целиком. Он содержит исправление M3U8 writer и переносимые тесты STEP-052. Прежние Linux 9/9 относятся к предыдущему source digest и сохраняются как историческое evidence; приёмка исправленной версии продолжается отдельно. Git, Python, отдельная установка Yarn и ручное создание папок для проверки не требуются.

## Перед запуском

Сценарий принимает HTTPS-ссылки на `music.yandex.ru`, `music.yandex.by`, `music.yandex.kz`, `music.yandex.com` и `music.yandex.uz`. В старом комплекте проверка инструмента ошибочно ограничивала домен до `.ru`; для обновления достаточно заменить `docs/research/step-027-acceptance/run.mjs`, сохранив свой `config.json`, установленный Node и зависимости.

1. Установить **Node.js 24** с официального [сайта Node.js](https://nodejs.org/en/download). Если Node уже установлен, `node --version` должен показать `v24.*`. Подходит также Node 22 начиная с 22.13.0; Node 25/26 не подходят этой версии проекта.
2. Распаковать архив в обычную папку на локальном диске с правом записи, например `Downloads/music-downloader-acceptance`. Не запускать внутри ZIP, в `Program Files` или из-под другого пользователя/администратора. На Windows желательно выбрать короткий путь, чтобы избежать ограничения длины имён при установке зависимостей. Общая папка VirtualBox на Z: уже дала EISDIR при создании workspace-ссылок Yarn; перенос на локальный диск позволил установить зависимости.
3. Нужны интернет, браузер, аккаунт Яндекс Музыки с доступом к выбранному контенту и примерно **10 ГБ свободного места**. Измеренный объём девяти циклов на Linux — около 2,9 ГБ аудио; зависимости и сборка занимают дополнительное место. FFmpeg необязателен для базовой проверки. Тестирование выполняется на самой Windows/macOS, без WSL или Linux-контейнера.

## Запуск: одна команда

Открыть терминал в корне распакованной папки. На Windows: в Проводнике открыть папку, в адресной строке набрать `powershell` и нажать Enter. На macOS: открыть Terminal, набрать `cd `, перетащить распакованную папку в окно и нажать Enter.

В обеих ОС запустить:

```text
node docs/research/step-027-acceptance/run.mjs
```

Сначала скрипт попросит **три свои ссылки**: трек, альбом и плейлист или коллекцию «Мне нравится», доступные аккаунту проверяющего. В альбоме и плейлисте нужны хотя бы два доступных трека; для минимального объёма проверки удобно выбрать небольшие коллекции. Выбирать полные треки обычной длительности, лучше не короче минуты: нужно успеть скачать физический prefix и прервать загрузку до её завершения. Заранее выбранных ссылок в комплекте нет. Редактировать файлы для обычного запуска не требуется.

Далее скрипт сам устанавливает закреплённые зависимости через Corepack/Yarn, выполняет lint/typecheck/test/build и дополнительные offline-проверки, проверяет механизм Ctrl+C, account и doctor. Временный NETWORK_ERROR в doctor автоматически повторяется до трёх попыток; все попытки сохраняются в отчёте. Если авторизации ещё нет, открывается штатный вход через браузер: нужно подтвердить его своим аккаунтом. В диалоге macOS Keychain разрешить доступ штатному CLI. Токены, пароли или cookies в команды вводить и кому-либо отправлять не требуется. Вход сохраняется в системном secure storage для последующих CLI-процессов.

После входа скрипт выполняет **девять реальных циклов**: три track, три album, три playlist. В каждом новая папка/задание, реальный Ctrl+C после скачанных байтов, проверка paused/exit 4, новый процесс resume, проверка completed/exit 0. Для коллекций прерывание происходит после завершения первого трека; проверяется, что этот файл не перезаписан. Проверяются аудио, теги, обложки, выбранное качество, manifest, отсутствие временных файлов и секретов на наблюдавшихся поверхностях.

Руками прерывать процесс, запускать resume или создавать папки не надо. Окно терминала оставить открытым до финального результата. На время проверки отключить автоматический сон компьютера; настройки скрипт не меняет. Продолжительность зависит от сети и размера плейлиста; ориентир — **20–60 минут**, при медленной сети дольше. На Linux штатный retry восстановил промежуточные сетевые сбои; сам по себе такой повтор не означает FAIL.

## Что отправить после проверки

В начале и в конце выводится полный путь, например:

```text
Отправить только: C:\Users\имя\music-downloader-check-XXXXXX\report.json
```

Папка отчёта создаётся в текущей папке запуска, а scratch тестов — в `.cache/checks` checkout. **Отправить только `report.json`**, даже если результат FAIL. Архив исходников, аудио, credentials, содержимое keyring и полные терминальные логи отправлять не нужно. JSON содержит все ячейки, версии среды/исходников/сборки, команды/коды, факты прерывания и проверки файлов; raw DTO/ошибки и значения credentials не записываются. Абсолютные пути локальных папок и публичные названия треков могут присутствовать.

Для полной успешной проверки в конце должны быть `Результат: PASS, циклов 9/9`, а в JSON — `mode: full`, `status: PASS`, `passedCycles: 9`. `SMOKE_PASS`, частичный отчёт или успешная установка зависимостей не заменяют полную приёмку. Пустой/неполный отчёт тоже полезен: его нужно отправить вместе с названием последней стадии, если скрипт был закрыт вручную.

Отчёт каждой ОС — evidence, а не автоматическое разрешение начинать UI: финальный go остаётся решением владельца после всей матрицы.

## Если возникла проблема

Скрипт останавливается на первом невыполненном условии, сохраняет уже полученные результаты и `failureCode`, возвращает exit 1. При FAIL отправить `report.json`; повтор без изменения приложения запускается той же командой и создаёт новую папку. Старые аудиофайлы и задания автоматически не удаляются. При изменении приложения результаты нужно сверить с предметом приёмки, а не смешивать версии.

Если не прошла установка зависимостей, в версии runner 2 доступен короткий запуск:

```text
node docs/research/step-027-acceptance/run.mjs --diagnose-install
```

Он не запрашивает ссылки, не авторизуется и не запускает музыкальную матрицу. Проверяет Corepack, доступ к registry.npmjs.org/repo.yarnpkg.com и повторяет только `install --immutable`. В `report.json` сохраняет версию/exit Corepack, HTTP status либо безопасный DNS/TLS/network code, наличие proxy/CA настроек без их значений, известные коды Yarn/ОС и категории ошибок установки. Raw stdout/stderr, native error messages, адреса из ошибок и секреты не сохраняются; диагностические признаки не объявляются доказанной первопричиной.

Отправить новый `report.json`. `INSTALL_PASS` означает только успешную установку; девять музыкальных циклов ещё не выполнены. После устранения причины запуск полной проверки остаётся прежним. Для runner 1 сначала заменить инструментарий на runner 2: старый отчёт содержит только hashes установки и по нему причина не восстанавливается.

Значения `YN0000`/`YN0002` и другие informational/warning codes сами по себе не означают отказ. Например, `YN0028` означает, что immutable install потребовал бы изменить lockfile; это отличается от сетевой ошибки. Интерпретация опирается на [коды Yarn](https://yarnpkg.com/advanced/error-codes) и [Corepack troubleshooting](https://github.com/nodejs/corepack#troubleshooting). Диагностические HTTP probes не заменяют реальную установку: она отдельно проверяет downloads, checksum и файловую систему.

| Код / ситуация                                                        | Действие                                                                                                                                                                                                                                                                |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INSTALL_FAILED` / старый `INSTALL_FAILED_CHECK_COREPACK_AND_NETWORK` | Выполнить `--diagnose-install` в runner 2 и отправить новый report.json; конкретное исправление выбирается по фактическим кодам.                                                                                                                                        |
| `SOURCE_SUBJECT_MISMATCH`                                             | Распаковать исходный архив заново; файлы не редактировать.                                                                                                                                                                                                              |
| `AUTH_FAILED` / `ACCOUNT_UNAUTHORIZED`                                | Повторить запуск и завершить штатный вход в браузере; убедиться, что аккаунт имеет доступ к музыке.                                                                                                                                                                     |
| `INSUFFICIENT_DISK_SPACE`                                             | Освободить место на диске домашней папки и повторить.                                                                                                                                                                                                                   |
| `EXISTING_LOG_FILE_CONFIGURED`                                        | Сообщить владельцу проверки. Существующий `settings.json` скрипт не изменяет: дополнительный log-file мог бы сохранить данные вне отчёта.                                                                                                                               |
| `INTERRUPTION_MECHANISM_FAILED` / `WINDOWS_CTRL_C_NOT_CONFIRMED`      | Отправить отчёт. На Windows помощник требует штатный Windows PowerShell и возможность компилировать небольшой C#-фрагмент через Add-Type; корпоративная политика может это запретить. Не обходить системную политику и не считать аварийное завершение успешной паузой. |
| Другой FAIL                                                           | Отправить отчёт; он содержит безопасные коды CLI и последнюю незавершённую ячейку.                                                                                                                                                                                      |

Для запуска без вопросов можно заранее заполнить **только `sources`** в `config.json` своими доступными ссылками: поля `track`, `album`, `playlist`. Тогда скрипт сразу использует их. Список `sourceFiles`, `gitHead` и `expectedSourceDigest` не менять. Скрипт проверяет полный provider-reported состав и не обходит ограничения доступа; выбранные ссылки сохраняются в отчёте.

## Для сопровождающего приёмку

Полный запуск в уже установленной/собранной копии: `node docs/research/step-027-acceptance/run.mjs --no-prepare`. Этот режим честно отмечает пропуск preparation; использовать, только когда актуальные supporting checks уже подтверждены на этой копии. Короткая проверка одного track-цикла: `node docs/research/step-027-acceptance/run.mjs --no-prepare --smoke`; `SMOKE_PASS` не прибавляется к обязательным девяти.

Offline-проверка самого runner: `node --test docs/research/step-027-acceptance/run.test.mjs`. Она содержит настоящий отдельный signal-probe process; probe не считается загрузкой. Упаковка текущего subject: `python3 docs/research/step-027-acceptance/package.py --replace`; в корне checkout создаются `STEP-052-acceptance.zip` и `STEP-052-update.zip`. Полный архив содержит верхнюю папку `music-downloader-acceptance`; короткий update-архив плоский, его распаковывают поверх уже открытого checkout. Затем выполнить `node docs/research/step-027-acceptance/apply-update.mjs`: собственные `sources` сохраняются, а identity subject обновляется. Python нужен только сопровождающему, не коллегам.

Если установка, lint/typecheck/test/build и дополнительные offline-проверки уже прошли на этой копии, а отчёт остановился на `WINDOWS_CTRL_C_NOT_CONFIRMED` с `signalProbe.code: 4` и результатом `paused`, полный preparation повторять не требуется. Исправленный `windows-cli.ps1` ждёт записи подтверждения из control-потока перед выходом helper: быстрый выход дочернего Node раньше обрывал этот фоновый поток. Проверка `CTRL_C_SENT` сохраняется; её отсутствие по-прежнему означает FAIL. После короткого update продолжить командой `node docs/research/step-027-acceptance/run.mjs --no-prepare`; сначала выполняется signal-probe, затем реальные загрузки. Самостоятельная offline-проверка runner на Windows повторяет быстрый native exit трижды; Linux-прогон не заменяет эту проверку.

На macOS/POSIX автоматическое прерывание — SIGINT. На Windows `child.kill('SIGINT')` резко завершает процесс, поэтому helper запускает только тестовый Node в отдельной скрытой консоли и посылает `CTRL_C_EVENT` через AttachConsole/GenerateConsoleCtrlEvent. PowerShell запускается с ExecutionPolicy Bypass только для этого процесса, постоянная политика не меняется. Это не отменяет более строгую корпоративную политику. Основания: [Node.js child_process](https://nodejs.org/api/child_process.html), [GenerateConsoleCtrlEvent](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent), [Creation of a Console](https://learn.microsoft.com/en-us/windows/console/creation-of-a-console).

Проверка runner на Linux доказывает Linux-механизм и формат evidence. Работоспособность Windows helper и macOS Keychain подтверждается только фактическими прогонами коллег на этих ОС; пока они pending. Новый source digest включает исправление STEP-052 и отличается от прежнего Linux evidence. Для STEP-052 требуется реальная успешная Windows test stage нового комплекта; полная матрица трёх ОС остаётся приёмкой STEP-027. Файлы этого инструмента находятся в audit/research scope и не входят в product source fingerprint.
