# Выпуск Yandex Music Downloader

Работай из корня checkout репозитория `yarkovaleksei/yandex-music-downloader`. Механические операции выполняет `apps/desktop/scripts/release.mjs`; устройство обновлений и требования к окружению описаны в `docs/development.md`, раздел «Публикация portable-релиза через GitHub Releases».

## Версия и описание

1. Выполни `yarn release plan` либо `yarn release plan --version <версия>`, если пользователь указал версию. Команда только читает Git/GitHub и допускает незакоммиченные изменения. План относится к HEAD; грязное дерево означает, что изменения ещё не вошли в выпуск.
2. Используй `previousTag`, `previousRevision`, `revision` и `commits` из результата. Предыдущий выпуск определяется по опубликованным stable-релизам, а не по любому локальному тегу. Посмотри существенный diff от `previousRevision` до `revision`; сообщения коммитов сами по себе не доказывают наличие функции. Если предыдущего выпуска нет, изучи README и текущие возможности приложения.
3. Предложи SemVer: patch для исправлений, minor для новых возможностей, major для несовместимых изменений стабильного контракта. Автоматическая версия в плане — только начальная рекомендация: первый выпуск `0.2.0`, затем следующий patch. Не переиздавай существующий выпуск без прямого поручения пользователя; не обновляй версии private workspace-пакетов: версия готового приложения берётся из тега.
4. Напиши описание по-русски и сохрани его в игнорируемом `.cache/releases/notes-<версия>.md`. Для первого выпуска опиши продукт, доступные платформы и установку. Для следующих — полезные пользователю изменения от предыдущего выпуска. Добавляй необходимые действия при обновлении и известные ограничения, когда они действительно есть; не заполняй пустые разделы и не переноси в текст внутреннюю историю разработки.

Пути, имена файлов и упоминания документов в описании оформляй Markdown-ссылками, если для них есть доступный адрес. Для пакетов используй прямые версионные URL `https://github.com/yarkovaleksei/yandex-music-downloader/releases/download/<tag>/<имя-файла>`: таблица установки должна позволять сразу скачать нужный пакет.

В поставке четыре portable-пакета: Linux x64 AppImage, Windows x64 exe, macOS arm64/x64 ZIP. Обновление проверяет подпись и скачивает пакет; пользователь закрывает приложение и заменяет файлы вручную. Ed25519-подпись описания не является системной подписью Apple/Microsoft. Не обещай автоматическую установку или отсутствие предупреждений ОС.

## Подготовка и публикация

Учитывай точный объём поручения. Запрос написать или проверить скрипт, спланировать релиз либо подготовить описание не разрешает публикацию. Явное поручение выпустить согласованную версию разрешает соответствующие операции; не проси повторного разрешения на уже порученное. Прямой запрет на коммиты, теги или публикацию имеет приоритет.

- `yarn release prepare --version <версия> --notes .cache/releases/notes-<версия>.md` требует чистого дерева, создаёт только локальный аннотированный тег и готовит подписанный комплект. Ничего не отправляет на GitHub. При поручении только спланировать выпуск остановись до этой команды: даже локальный тег меняет Git.
- Скрипт не создаёт коммиты и не отправляет ветку main. Если рабочее дерево грязное, подготовь план и описание, затем сообщи, что для сборки нужно отдельно зафиксировать исходники. Не обходи проверку чистоты, не собирай другой commit и не включай в релиз чужую незавершённую работу.
- Перед публикацией исходный commit комплекта должен находиться в main на GitHub; тег и manifest закрепляют именно этот commit. HEAD инструмента публикации может быть новее исходного commit комплекта. Выполни `yarn release publish --version <версия>` только в рамках поручения выпустить эту версию. Команда отправляет точный тег, создаёт draft, загружает и проверяет 12 вложений, публикует как latest и повторно проверяет метаданные всех вложений через GitHub API.
- При сетевом сбое повтори ту же команду один раз, если разрешение на выпуск сохраняется. Уже загруженные совпадающие файлы используются повторно; скрипт сам удаляет только пустые незавершённые `starter`-вложения draft. При повторном отказе остановись и сообщи этап сбоя. Несовпадение SHA-256, описания или Git-состояния требует разбирательства, а не удаления релиза, `--clobber`, переноса тега или новой сборки под опубликованным номером.
- Если релиз уже опубликован, повторный publish проверяет его и сохраняет публичную квитанцию; опубликованные файлы не меняются. Отказ после публикации не означает, что релиз остался draft: проверь фактическое состояние и сообщи его пользователю.

Для проверки вложений сравнивай локальные SHA-256 и размеры с `digest` (`sha256:<хэш>`), `size` и состоянием `uploaded` из GitHub API; проверяй полный состав из 12 файлов и их версионные URL. **НЕ СКАЧИВАЙ ВЛОЖЕНИЯ ОБРАТНО ДЛЯ ПРОВЕРКИ.** Отсутствующий или несовпадающий digest останавливает проверку; скачивание не используется как запасной способ. Это проверка хэшей GitHub, а не фактического публичного скачивания.

При прямом поручении переиздать ту же версию сначала сохрани описание, исходный тег и комплект в резервную копию. Удали только согласованные релиз и тег, затем выполни обычные prepare и publish из зафиксированных исходников. Сохрани прежнее описание, если пользователь не поручил его изменить.

Существующий ключ подписи берётся из системного хранилища Linux. Не запускай `init-key` автоматически, не меняй production trust, не извлекай ключ в файл/окружение и не записывай секреты или подписанные CDN URL в описание и отчёт.

## Проверка результата

Для изменений релизного кода используй `yarn test:release`; для него нужен существующий desktop dist текущих исходников (`yarn build`). Тесты работают с временными репозиториями, пакетами и ключами, без публикации на GitHub. Проверка скилла и скрипта не требует настоящего выпуска.

В результате укажи версию, точный commit, выполненный этап, состояние GitHub и применимые проверки. Публикацию подтверждает результат `published: true, assetsVerified: true, verification: "github-api-sha256"` и квитанция `.cache/desktop-packaging/<tag>/public-release.json` с методом проверки и хэшами всех 12 вложений. Не выдавай изолированные проверки за реальную загрузку пакетов или нативный запуск Windows/macOS.
